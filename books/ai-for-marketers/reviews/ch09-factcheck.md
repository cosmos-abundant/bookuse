## 1. 외부 사실 검증

### 1-1. CrowdStrike 2024 사고 (27행) — 확인

원고 서술: "2024년 7월 19일, 보안업체 CrowdStrike가 Windows용 센서에 배포한 단 하나의 결함 있는 설정 업데이트가 약 850만 대의 Windows 기기를 부팅 불능에 빠뜨렸고, 항공·은행·병원·긴급전화 서비스가 전 세계에서 동시에 마비됐다."

- 날짜 2024-07-19: 확인 (Wikipedia, TechCrunch, CISA alert 2024/07/19, Help Net Security 모두 일치).
- 약 850만 대: 확인 (Microsoft 공식 추정치 8.5M — TechCrunch 2024-07-20, Malay Mail, Wikipedia "Roughly 8.5 million systems"). 원고가 "약"으로 완화 표기한 것 적정.
- 결함 있는 설정 업데이트(Channel File 291): 확인 (Wikipedia — Channel File 291 logic error, timestamp 2024-07-19 0409 UTC 버전만 결함). 원고는 본문에서 "Channel File 291" 파일명을 쓰지 않고 "단 하나의 결함 있는 설정 업데이트"로 일반화 — 정확하며 더 안전한 서술.
- 피해 부문(항공·은행·병원·긴급전화): 확인 (Wikipedia "airlines, police departments, banks, hospitals, emergency call centers"). "긴급전화 서비스 = emergency call centers" 정합.

비고: 카드 04가 "집필 전 CrowdStrike 공식 PIR 원문 재확인 권장"으로 남긴 항목. 공식 PIR 원문 직접 열람은 이번에도 안 했으나(접근 비대상), 본문이 인용한 모든 수치·날짜·부문이 복수 2차 출처(Microsoft 1차 추정치 포함)에서 교차 일치하므로 본문 서술 수준에서는 검증 충분. 본문이 회사 사후보고서의 직접 인용 문구를 쓰지 않으므로 PIR 표현 대조는 불요.

- 수위 점검: 28행에서 "당신 자동화도 850만 대처럼 터진다는 말이 아니라... 구조 원리의 극단적인 예시로만 가져온다"로 명시적 단서. 카드 04의 겁주기·과장 방지 지시 충실 반영. 통과.

### 1-2. Google SRE — "연쇄 실패의 가장 흔한 원인 = 과부하" (17행) + 무한 재시도(19행) — 확인

원고 서술(17행): "Google의 사이트 신뢰성 공학 교범은 연쇄 실패의 가장 흔한 원인을 과부하로 정리한다."

- 확인: SRE Book Ch.22 "Addressing Cascading Failures" 원문 "The most common cause of cascading failures is overload. ... either directly due to server overload, or due to extensions or variations of this scenario." 검색 추출 + IPFS 공식 미러 + High Scalability 요약 교차 일치.
- sre.google 공식 페이지는 이번에도 HTTP 403(카드 예고대로). 교차 출처로 확정 — **[원문 403 → 교차 확인]**.
- 무한 재시도(19행 "무한 재시도를 걸지 않는다... 한도를 더 빨리 태우고 문제를 키운다"): 확인. SRE Ch.22가 "retries can amplify load... amplify low error rates into higher levels of traffic, leading to cascading failures"로 명시. 원고의 "재시도 = 한도를 더 빨리 태움" 번역은 마케터 맥락(트래픽→한도)으로 정확히 옮긴 것.
- 과부하 → 마케터 번역(API/실행 횟수/토큰 한도, 17행): 카드 02 인용 방식 제안과 정합. SRE 대규모 분산 맥락을 "원리만 차용"한다는 카드 지시도 28·29행 단서로 반영됨. 통과.

비고: 카드가 "직접 인용 문구는 sre.google 원문에서 확정" 권고했으나, 본문은 따옴표 직접 인용을 하지 않고 요지만 풀어 씀("가장 흔한 원인을 과부하로 정리한다"). 따라서 글자 단위 인용 대조 대상 아님 — 요지 일치만 확인하면 충분하며 일치함.

## 2. 개념 서술 정확성

### 2-1. 강한 결합 / 느슨한 결합 (13·15행) — 확인
- 강한 결합="구성 요소들이 서로의 내부에 직접 의존하며 얽혀 있는 구조", 느슨한 결합="약속된 입출력 형식으로만 최소한으로 주고받는 구조", 한 부품 교체 시 나머지 무영향 — 카드 01 주장과 정합. 시스템 공학 표준 정의에 부합.

### 2-2. 연쇄 실패 (13·17행) — 확인. 카드 01·02 정합.

### 2-4. bus factor (78행) — 확인
- "어떤 시스템을 유지하고 운영할 지식을 몇 사람이나 가지고 있느냐를 재는 지표 / 버스 팩터 1 = 아는 사람이 단 한 명" — 카드 05 정의와 정합. Wikipedia "Bus factor" 표준 정의 부합.
- 어원 서술("핵심 인원이 버스에 치이면 이 일이 멈추는가") 정확.
- 규모 수위: 78행 "회사 핵심 인프라 같은 거창한 위험은 아니지만, 개인 차원에서는 분명한 약점" — 카드 05 "규모 과장 금지" 지시 반영. 통과.

### 2-5. 런북/인수인계 (80행) — 확인

### 3-1. bus factor 정량 수치("주당 10% 낭비, 53% 지연, 37% 하락") — 누출 없음 (통과)

### 3-2. "주간 점검 평균 시간" 정량 통계 — 누출 없음 (통과)

## 5. 시점([휘발성]) 및 [확인필요] 점검

### 5-1. 시점 명시 — 통과
- 7행 박스 "2026년 6월 기준." 명시.
- CrowdStrike 사건: 본문에 "2024년 7월 19일" 시점 병기(27행). 카드 04 [휘발성] 지시(2024년 7월 시점 병기) 준수.
- 도구 휘발성 세부는 5~8장 버전 박스 + 12장으로 위임(7행)한다고 명시 — 본 장이 휘발성 정보를 떠안지 않음. 적정.

### 5-2. [확인필요] 1건 (48행) — 정직성 통과 / 발행인 처리 권고

원고 표시: `[확인필요: 통합 후 주간 검수 시간 분산 — 베타 리더 실측, ch06 과업 D와 연동]`

- 정직성 판정: **정직.** 48행은 "그 40분의 정확한 숫자는 베타 리더 실측 전까지 목표로만 적는다고 했다... 통합한 뒤 검수가 한 주에 정확히 몇 분으로 흩어지는지는 단정할 수 없다"로 한계를 먼저 고백한 뒤 표시. 카드의 미확인 목록 2번·과업 D 연동 방침과 정확히 일치. 단정으로 새지 않음.
- 해소 가능성: 감수자가 외부 사실로 해소할 수 없는 항목(발행인 자체 실측 대기값). 따라서 게이트의 "[확인필요] 0건"은 사실 검증으로 닫히지 않음.

**발행인 처리 권고(택1):**
1. (슬롯 유지) 베타 리더 실측 일정이 출간 전 잡혀 있으면 슬롯을 유지하고, 실측 후 구체 분산값으로 교체. 이 경우 출간 전 본 표시 반드시 해소.
2. (본문 자기완결) 실측이 출간에 못 맞거나 불확실하면, 48행을 본문 자기완결형으로 다듬는다. 본문은 이미 "정확히 몇 분인지 단정 못 함 + 구조는 표가 보여 줌"으로 논지가 완결돼 있으므로, [확인필요] 괄호만 제거하고 "구체 분산값은 6장 과업 D의 실측에 위임한다" 정도의 평서문으로 전환하면 사실 공백 없이 닫힌다. 권고: 이 장은 원리 장이라 정량값이 본문 논지에 필수가 아니므로 **2안(본문 자기완결)이 안전.**
