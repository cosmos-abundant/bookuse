- 자료카드: `books/ai-for-marketers/research/ch10-failures.md` (신규 카드 01~13, 재활용 4건, 미확인 8건)

## 1. 실패 모드 사실 (카드 01~06 대조 + 2026-06-13 유효성)

### 1-1. OAuth 토큰 만료 조건 (패턴 1, 카드 01) — 확인
- 본문(29~31행): "출입증은 영구권이 아니라 주기적으로 갱신… 갱신 없이 오래 방치되거나, 도구가 갱신을 시도하다 막히면 무효." **구체 일수("6개월")를 본문에 쓰지 않음 — 카드의 [휘발성] 지침 준수.**
- 외부 재확인(2026-06-13, WebSearch 추출): Google for Developers OAuth 2.0 문서가 ⓐ 6개월 미사용 ⓑ 비밀번호 변경(Gmail 범위 포함) ⓒ 접근 권한 회수 ⓓ 리프레시 토큰 최대 개수 초과 — 4조건으로 토큰이 무효화됨을 명시. 카드 01과 일치. 카드가 403으로 원문 미열람이라 했으나, 본 감수에서 공식 문서 발췌로 교차 확인 완료.
- 판정: **확인.** 본문은 메커니즘만 서술해 휘발성 위험 없음. 9행 "2026년 6월 기준" 박스가 시점을 명시함.

### 1-2. 인증 만료 시 노코드 도구 동작 — Zapier 반복 오류 자동 OFF (패턴 1, 카드 02) — 확인
- 본문(31행): "노코드 도구는 같은 오류를 반복하다 워크플로 자체를 꺼 버린다. Zapier 공식 도움말은 이를 분명히 적어 둔다 — Zap이 반복적으로 오류를 내면 자동으로 꺼진다."
- 외부 재확인(2026-06-13): Zapier Help Center "How to troubleshoot errors in Zap workflows"가 "If a Zap errors repeatedly, it will automatically turn off"를 명시. 추가로 발견한 구체 메커니즘("최근 7일 실행의 95%가 오류 시 자동 OFF")과 플랜별 유예시간(Team 24h·Enterprise 72h)이 실재하나, **본문은 이 수치를 일절 쓰지 않음 — 카드 미확인 목록 지침 정확히 준수.**
- 판정: **확인.** 인용도 정확("반복적으로 오류를 내면 자동으로 꺼진다"). 수치 누출 없음.

### 1-3. 권한·비밀번호 변경 시 토큰 회수 (패턴 2, 카드 06) — 확인
- 본문(43행): "Google Workspace 공식 문서는 비밀번호를 변경하면 특정 제품의 연동 토큰이 자동으로 회수된다고 적어 둔다."
- 외부 재확인(2026-06-13): Google Workspace Admin Help "Automatic OAuth 2.0 token revocation upon password change"(support.google.com/a/answer/6328616)가 정확히 이 내용을 명시. 본문 표현 "특정 제품의"가 공식 문서의 "issued for access to certain products"와 정밀히 대응 — 회수 범위를 "모든 토큰"으로 과장하지 않고 한정함. **카드 미확인 목록의 "Google 토큰 회수 범위" 우려가 본문에서 정확히 한정 표현으로 처리됨.**
- 판정: **확인.** 표현 수위 적절("회수될 수 있다"·"특정 제품"으로 한정).

### 1-4. rate limit / 429 (패턴 4, 카드 04) — 확인
- 본문(61행): "서버는 '요청이 너무 많음'이라는 신호(HTTP 429)를 돌려보내고… 한도 창이 리셋될 때까지 추가 요청을 막는다. 이건 비정상이 아니라 서버가 과부하를 막는 표준 동작이다."
- 외부 재확인(2026-06-13): MDN "429 Too Many Requests"가 정확히 일치 — rate limiting 메커니즘, Retry-After 헤더. 본문 "좋은 노코드 도구는 이 신호를 받으면 잠시 기다렸다 다시 시도"는 Retry-After/백오프와 일치.
- **구체 한도 수치(분당/일일)는 본문에 단정 없음 — 카드 미확인 목록 준수.** "무료 한도가 너무 낮아서"(65행)도 일반 서술이지 특정 수치 아님.
- 판정: **확인.** (2-1 항목과 중복 확인.)

### 1-5. 스키마 변경 → NULL 통과 (패턴 5, 카드 03) — 확인
- 본문(71행): "소스가 'cost'라는 열 이름을 'spend'로 바꾸면, 자동화는 'cost' 칸을 못 찾고 그 자리를 비운 채 보고서를 완성한다." + "대부분의 도구가 오류를 내고 멈추지 않는다"(수위 한정).
- 카드 03 대조: 메커니즘(열 이름 변경→NULL→무음 통과) 일치. 카드 반대근거("항상 무음은 과장, 일부는 에러로 멈춤")를 본문이 "대부분의"·"많은 경우" 수위로 흡수. **다운타임 시간·금액 수치는 본문에 없음 — 카드 지침 준수.**
- 판정: **확인.** 예시(cost→spend)는 카드 인용 방식 제안과 동일한 일반 예시이며, 가짜 사례 아님(특정 회사·날짜 없는 메커니즘 예시).

### 1-6. 소스 구조 변경 → 빈 결과 (패턴 6, 카드 05) — 확인
- 본문(81행): "스크래핑 업계의 표현 그대로, 수집기는 요란하게 죽지 않고 조용히 죽는다 — 빈 결과를 돌려주면서."
- 카드 05 대조: 원문 "most scrapers don't fail loudly—they fail quietly... they return empty arrays"의 충실한 번역 인용. **유지보수 공수 40~60% 수치는 본문에 없음 — 카드 지침 준수.** 적용 범위 한정("화면을 긁어오는 수집형에만 해당… 광고 API 연동에는 적용되지 않는다", 83행)이 카드 반대근거를 정확히 반영.
- 출처 등급 메모: 카드 05는 2차(스크래핑 전문 매체). 본문이 "스크래핑 업계의 표현"으로 출처 성격을 정직하게 라벨링 — 1차 학술로 위장하지 않음. 적절.
- 판정: **확인.**

## 2. 오류 문구가 실재 표준인지 (MDN 등)

### 2-1. "429" / "too many requests" — 확인
- 본문(61·65·99·151행)에서 "429", "too many requests" 사용.
- MDN Web Docs "429 Too Many Requests"(2026-06-13 재확인): 정식 상태 텍스트가 "Too Many Requests"이며 rate limiting 신호임을 명시. Retry-After 헤더도 실재. **실재 표준 문구 확정.**
- 무결성 측면: 이 두 문구는 독자가 실행 기록에서 실제로 보게 되는 표준 문자열이고, 자료카드 무결성 메모가 "실재하는 것만 기록"으로 허용한 항목. 가짜 에러 메시지 아님.
- 판정: **확인.**

## 3. 모델 deprecation 경계 (패턴 3) — ch12와 모순 검사

### 3-1. 통지 기간 수치 일치 — 확인
- 본문 ch10(53행): "Anthropic은 최소 60일, OpenAI는 정식 모델 최소 6개월·프리뷰 2주, Google은 -latest 별칭 2주."
- ch12(27행) 대조: "Anthropic은… 최소 60일… OpenAI는 일반 공개 모델은 최소 6개월, 그 변형은 3개월, 프리뷰 모델은 2주… Google은… 별칭은… 2주 통지." **수치 완전 일치.**
  - 미세 차이: ch10은 OpenAI "변형 3개월"을 생략하고 "정식 6개월·프리뷰 2주"만 인용. 이는 축약이지 모순 아님 — ch10은 경계 박스 한 줄 요약이고 "자세한 정책은 12장"으로 명시 위임(53행). 적절한 분담.
- 카드 09 대조: Anthropic 60일·OpenAI 6개월/2주·Google -latest 2주 — 카드와도 일치.
- 판정: **확인.** ch12와 수치 모순 없음.

### 3-2. 경계 분담 로직 일치 — 확인
- ch10(55행): "출력이 아예 안 나오면 이 장(10장)… 출력은 나오는데 톤·골격만 달라졌다면 12장."
- ch12(23행): "출력이 아예 안 나오는 응급 상황은 10장이… 복구하고, 출력은 나오는데 톤·골격이 바뀐 경우는 12장이 명세 점검으로 받는다." **분담 방향 완전 일치, 상호 참조 정합.**
- GPT-4o 사례: ch10은 패턴 3에서 GPT-4o 실명·날짜를 쓰지 않고 12장으로 위임(53행). ch12(21행)가 "2026년 2월 13일 정식 은퇴"를 상세 서술. 카드 09와 일치. 중복·모순 없음.
- 판정: **확인.** 두 장이 같은 현상을 다른 증상으로 분담, 모순 0.

## 4. 무음 실패 위험성 · 비개발자 트러블슈팅 2원칙 (카드 07·10)

### 4-1. 무음 실패 위험성 (패턴 7, 카드 07) — 확인
- 본문(123·125행): "정상적으로 돌면서 틀린 결과를 내는 것 — 이것이 런타임 오류로 멈추는 것보다 훨씬 진단하기 어렵다" + "틀린 데이터가 틀린 줄 모르고 계속 신뢰받다가, 이미 피해가 발생한 뒤에야 드러나기 때문."
- 카드 07 대조: "런타임 에러가 아니라 정상 작동하며 틀린 출력이 가장 어렵다"(IBM 인용) + "remain invisible until the damage is already done"의 충실한 번역. 일치.
- 출처 성격: 카드 07은 2차/3차(데이터 엔지니어링 매체), 학술 1차 미확인. 본문이 "업계 정리에 따르면"류 권위 단정을 피하고 정의·메커니즘 서술로 처리 — 카드 03·05와 교차 검증된 정성 주장이라 사용 가능 범위. 무리한 인용 없음.
- 판정: **확인.**

### 4-2. 트러블슈팅 2원칙 (카드 10) — 확인
- 본문(87~89행): ① "마지막으로 정상이던 이후 무엇이 바뀌었나" ② "한 번에 하나씩만 바꾼다" + "전문가는 추측하지 않고 순서를 따른다" + "좁히는 것이 다 해 보는 것보다 빠르다."
- 카드 10 대조: "make only one change at a time", "professionals who troubleshoot don't guess; they follow a sequence", "isolation is faster than trying everything" — 세 직접 인용 모두 충실 번역. 분할 정복 원리 일치.
- 네트워크 OSI 용어를 페르소나 언어로 번역(출력→연결→소스→실행 기록)하라는 카드 지침도 준수(91~99행).
- 판정: **확인.**

## 5. 무결성 검사

### 5-1. 가짜 에러 메시지·가짜 사례 0 — 통과
- 본문에 등장하는 기술 문자열: "429", "too many requests" — 둘 다 MDN 실재 표준(2-1 확인).
- 카드의 실재 오류 문구("invalid_grant", "This auth is expired" 등)는 **본문에서 화면 예시로 쓰지 않음** — 작가가 가공 화면 예시를 넣지 않고 메커니즘 서술로 처리. 무결성 지침 정확히 준수.
- 사례: 김지유(가상 인물)는 1행에서 "(1장부터 함께 온 가상의 인물이다)"로 명확히 라벨링. cost→spend(71행)는 메커니즘 예시이지 실명 사건 아님. **실명 회사·날짜를 가진 가짜 장애 사례 0건.**
- 판정: **통과.**

### 5-2. 패턴 1~7 번호 일관성 — 통과
- 7행·13행에서 "패턴 1~6=안 온다, 패턴 7=왔는데 틀렸다(무음 실패)" 구조 선언.
- 본문 전개: 패턴 1(연결 만료, 27행) → 2(비밀번호·권한, 39행) → 3(모델 은퇴, 49행) → 4(한도, 57행) → 5(소스 형식, 67행) → 6(소스 화면, 77행) → 7(무음 실패, 119행). **번호 누락·중복·역전 없음.**
- 진단 순서(99·101행)에서 각 단계가 잡는 패턴 매핑도 일관: 출력 자리→연결(1·2)→소스(5·6)→실행 기록(429=4, 모델=3). 패턴 7만 진단 순서 밖(검수)으로 정확히 배치.
- 판정: **통과.**

### 5-3. 체크리스트 빈칸 양식 — 통과 (주의 1건, 오류 아님)
- 149·151행의 밑줄 빈칸("______________")은 **독자 기입란**이며, 156행 표 캡션이 "독자가 자기 도구의 화면 위치를 직접 적어 넣는 기입란이다(작가 미완 표시가 아님 — 조판 시 밑줄 빈칸 양식으로 확정할 것)"로 명시.
- 판정: **통과.** 이는 의도된 양식이며 `[확인필요]`성 미완이 아님. 조판 시 밑줄 양식 확정 지시가 캡션에 살아 있음 — 발행인은 조판 단계에서 이 지시 이행만 확인하면 됨(팩트 문제 아님).

### 5-4. [확인필요] 잔존 — 0건 통과
- 전수 검색(확인필요/TODO/TBD/FIXME 등): **매치 0.** 잔존 마커 없음.
- 판정: **통과.**

| 모델별 통지 기간 | ch12 카드(1차 확인분)에서 인용, "자세한 건 12장" 위임 | 적정 인용 |
| rate limit 구체 수치 | 본문에 없음 — "429 메커니즘 + 주기 늦추기" 처방만 | 누출 없음 |
| 스키마/스크래퍼 공수 수치(40~60% 등) | 본문에 없음 — 메커니즘·인용구만 | 누출 없음 |

작가 보고("메커니즘만 쓰고 수치는 뺐다")가 **전 항목에서 사실로 확인됨.**

## 7. 원문 403 다수 — 교차 확인 결과 + 출간 전 재확인 명시

자료카드가 다수 1차 출처를 403(WebFetch 차단)으로 원문 미열람 처리했다. 본 감수에서 WebSearch 공식 발췌로 **4개 핵심 1차 출처를 교차 재확인 완료:**

1. **Google for Developers OAuth 2.0**(카드 01) — 6개월/비밀번호/회수/한도 4조건 확인.
2. **Zapier Help Center**(카드 02) — "반복 오류 시 자동 OFF" 확인.
3. **Google Workspace Admin Help 6328616**(카드 06) — 비밀번호 변경 시 토큰 자동 회수, "certain products" 한정 확인.
4. **MDN 429**(카드 04) — 표준 문구·Retry-After 확인.

본문이 이들 출처에서 **수치가 아니라 메커니즘만 인용**했으므로, 403 미열람의 위험(수치가 틀릴 위험)은 본문에 존재하지 않는다. 다만 [휘발성] 정책 항목이므로:

> **출간 전 재확인 권고(발행인 액션, 팩트 게이트와 무관):** 9행 "2026년 6월 기준" 박스가 시점을 명시하고 본문이 수치를 피했으므로 팩트 게이트는 통과한다. 출간 직전, 위 4개 1차 출처와 모델 은퇴 현황(ch12 위임분)을 한 번 더 눈으로 확인하면 신선도가 완벽해진다. 이는 게이트 차단 사유가 아니라 [휘발성] 자산의 통상 점검이다.

## 8. 최종 판정

- 검증 항목: **25건** (실패모드 6 + 오류문구 1 + 모델경계 3 + 무음/트러블슈팅 2 + 무결성 4 + 미확인누출 5 + 1차교차 4)
- **오류: 0건**
- **불확실: 0건**
- 해소해야 할 [확인필요]: 0건 (원래부터 0건)
- 무결성: **통과** (가짜 에러·사례 0, 패턴 1~7 일관, 체크리스트 빈칸은 의도된 독자 기입란, 마커 잔존 0)

**게이트 기준(오류 0건 + [확인필요] 0건) 충족 → 통과.**

작가가 자료카드의 "수치 배제, 메커니즘만, 시점 명시" 설계를 예외 없이 이행했고, 휘발성 위험을 본문 구조로 사전 차단한 모범 사례다. 발행인 액션은 출간 직전 [휘발성] 4건의 통상 신선도 점검 1회뿐이며, 이는 본 단계 게이트와 무관하다.
