# 챕터 브리프: ch12 (갈아타기 프로토콜 — 이 책의 도구가 낡았을 때)

⚠️ **집필 순서 주의:** 이 장은 3부지만 2부(ch05~09)보다 먼저 집필된다. 2부에서 짓는 구체 시스템을 **원리 수준으로만** 참조하고, 특정 도구의 구체 절차에 의존하지 마라. 2부 완성 후 편집장이 정합성 패스를 한다(STATUS 기록).

- **독자가 얻는 것 (한 줄):** 2027년에 도구 지형이 바뀌어도, 1부의 원리로 같은 시스템을 새 도구 위에 다시 짠다.
- **이 챕터가 답하는 질문:** "이 책대로 다 만들어놨는데 6개월 뒤 그 도구가 없어지거나 확 바뀌면? 내가 들인 시간이 다 날아가나?"
- **다뤄야 할 핵심 내용:**
  1. **이 책의 휘발성을 책 안에서 정면으로 인정한다.** 도입은 "이 책의 2부는 언젠가 낡는다 — 그것도 생각보다 빨리"를 회피하지 않고 선언. 이게 신뢰 장치다(다른 AI 책은 이 말을 안 한다).
  2. **낡는 순서 예측:** 무엇이 먼저 낡는가 — UI(버튼 위치) → 가격/플랜 → 기능 → 도구 자체의 존속. 각 단계가 독자에게 주는 충격과 대응 난도가 다르다. 실제 사례로(자료카드 — 단종된 도구, 가격 급변, 기능 폐지 실명 사례).
  3. **이식 자산 vs 폐기 자산:** 도구가 바뀌어도 살아남는 것(1부에서 만든 것 — 업무 명세[3장], 검증 체계[4장], 자동화 대상 판단[2장], 보조/위임/자동화 구분[1장])과 버려지는 것(특정 도구의 연결 설정, 버튼 경로). 1부가 왜 2부보다 오래 가는지를 여기서 회수.
  4. **새 도구 평가 5문항:** 새 도구로 갈아탈지 판단하는 체크리스트. (예: 내 명세를 그대로 받는가 / 데이터를 빼낼 수 있는가[락인 회피] / 검증 지점이 유지되는가 / 가격이 내 사용량에서 지속 가능한가 / 죽어도 대체재가 있는가) — 자료카드로 락인·데이터 이식성 근거.
  5. **갈아타기 실전 절차:** 도구가 죽었거나 바꿔야 할 때, 1부 자산을 들고 새 도구에 다시 올리는 단계별 절차. "처음부터"가 아니라 "명세는 그대로, 연결만 새로"임을 보인다.
- **다루지 않는 것:** 일상 장애 대응(10장 — 도구는 살아 있는데 일시적으로 깨진 경우. 이 장은 도구 자체가 낡거나 죽는 경우. 둘의 구분을 명시). 보안(11장). 2부 특정 도구의 구체 재설정 절차(원리만).
- **자료카드:** `research/ch12-migration.md`
  - 실제로 단종/대폭 변경된 AI·자동화 도구 사례(서비스 종료, 가격 정책 급변, 무료→유료 전환, 기능 폐지, 모델 단종/deprecation). 실명·출처·날짜 필수. [휘발성].
  - 벤더 락인(vendor lock-in)과 데이터 이식성(data portability)의 근거 — 개념·실무 권고(1차 우선).
  - 모델 deprecation 관행(OpenAI/Anthropic/Google이 구 모델을 어떻게 단종하는지, 공지 기간 등) [휘발성].
  - ch05 스파이크에서 나온 "아임리포트 같은 서드파티 SaaS 의존이 12장 최상위 리스크"(research/ch05-spike.md)를 이 장의 사례로 연결 검토.
- **예상 분량:** 8,000자 (±20%)
- **앞뒤 챕터 연결:** 1부 전체(명세·검증·판단이 이식 자산)를 회수. 11장에서 받음(보안), 책의 마지막 장 — 닫는 메시지. 2부 도구들이 "낡을 수 있음"을 전제로 함(원리 참조).
- **스타일 유의:** ai-howto(휘발성 관리의 정수가 이 장 — 버전·시점 명시, 원리와 절차 분리의 모범) + practical + common + 용어집. 책의 마지막 장이므로 "그래서 이 책은 낡어도 당신은 안 낡는다"는 마무리 톤. red-team이 기획에서 이 장을 신뢰 장치로 높이 봤으니, 공허한 안심이 아니라 실제로 작동하는 프로토콜이어야 함.
